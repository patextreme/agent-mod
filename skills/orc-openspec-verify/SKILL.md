# OpenSpec Verification Orchestration

Act only as the orchestrator: delegate investigation, verification, edits, and checks to subagents. Use the installed `openspec-verify-change` skill as the verification procedure. Keep rounds in the same repository and selected change/store; run verification and repair sequentially so each verification sees completed edits.

## Installed dependencies

Resolve `openspec-verify-change` from the invoking environment's available-skill information. Read the resolved SKILL.md and pass its absolute path, together with explicit repository/worktree and applicable change/store context, to delegates. If a required skill is unavailable, pause with the missing prerequisite; do not invent a checkout or home-directory path or substitute another procedure.

## Execution

Read [the orchestration pseudocode](./references/pseudocode.md) before launching agents. Adapt it into codemode calls or a `SubagentWorkflow` script: use codemode for incremental, judgment-heavy coordination and SubagentWorkflow for deterministic loops and pipelines. The pseudocode defines control flow; the stage contracts below define delegated work and completion criteria. Retain orchestrator judgment for assessing evidence, preparing repair briefs, and escalating decisions. With either tool, human-input branches must pause execution and resume explicitly with the user's answer.

## Stage contracts

1. **Verify.** Spawn a fresh read-only `general-purpose` Agent. Pass the repository path, requested change/store, and absolute verification skill path. Require it to read and follow that skill and project instructions, load all available context artifacts, and inspect the implementation. Have it return the resolved change/store, artifact paths, full report, Critical/Warning/Suggestion counts, checks run with results, and checks skipped with reasons. If selection is ambiguous, relay the available choices to the user; keep the resolved change/store sticky for later rounds.
2. **Decide.** Read the returned report. End successfully only after a fresh, complete verification reports zero **Critical** and zero **Warning** findings. This is stricter than the underlying skill's warning-only archive assessment. Suggestions do not drive repairs; surface them in the final report. Missing optional artifacts may justify skipped checks under the verification skill's graceful-degradation rules; disclose that limited scope. An interrupted review, unread available artifact, blocked required check, or indeterminate severity is not success: delegate the missing investigation or escalate the limitation.
3. **Repair.** If Critical or Warning findings remain, spawn a separate `general-purpose` Agent with the exact change/store, repository path, artifact paths, and full report. Require it to investigate each finding and repair both severities, prioritizing Critical findings and respecting dependencies. Scope edits to the implementation, tests, and directly affected change artifacts; preserve unrelated work and leave Suggestions alone. Follow project instructions and applicable behavioral specs. Prefer bringing code into alignment with recorded intent; reconcile artifacts only for evidence-backed bookkeeping or already-authorized decisions. Mark tasks complete only after inspecting their implementation and checks. Do not weaken requirements, tests, or severity merely to clear the report. Require relevant checks, a summary of actual edited files, a per-finding disposition with evidence, check commands/results, and unresolved blockers.
4. **Escalate when needed.** Attempt fixes autonomously when existing requirements, recorded decisions, and repository conventions determine the correction. If resolution requires new product intent, a consequential architecture or risk decision, unavailable access, or cannot be established safely, have the subagent return the finding, investigation and attempted fixes, exact blocker, and specific question/options with consequences. Preserve completed safe repairs, pause the loop, and ask the user for the needed input. Resume with that input and the same change/store. A suspected false positive requires evidence and fresh verification, not silent dismissal.
5. **Repeat.** After repairs finish, return to step 1 with a fresh verification agent. Require it to inspect the actual diff and independently verify previous findings, new regressions, and relevant check results; a repair summary alone is not proof. Continue without an arbitrary round limit. If an agent fails or findings recur without substantive progress, report the impediment and request human input rather than repeat unchanged work indefinitely or claim success.
6. **Finish.** Report the change/store, verification and repair round counts, edited files, final Critical/Warning/Suggestion counts, checks and results, skipped scope, and any unresolved questions. Clearly distinguish verified success from a blocked or partial run. Leave archiving and spec syncing to separate user requests; zero findings alone does not prove structural validity or passing checks that were not run.
