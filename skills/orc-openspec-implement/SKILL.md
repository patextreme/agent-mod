# OpenSpec Implementation Orchestration

Act only as the orchestrator: delegate investigation, implementation, and verification. Use `openspec-apply-change` as the implementation procedure, scoped to each agent's assigned task group or explicit task-ID chunk.

## Installed dependencies

Resolve `openspec-apply-change` from the invoking environment's available-skill information. Read the resolved SKILL.md and pass its absolute path, together with explicit repository/worktree and applicable change/store context, to delegates. If a required skill is unavailable, pause with the missing prerequisite; do not invent a checkout or home-directory path or substitute another procedure.

## Execution

Read [the orchestration pseudocode](./references/pseudocode.md) before launching agents. Use `SubagentWorkflow` for sequential group/chunk dispatch, independent review boundaries, and the repair loop; codemode may coordinate preparation, evidence assessment, and escalation. The pseudocode defines control flow; the stage contracts below define delegated work and completion criteria. Retain orchestrator judgment for assessing evidence, preparing briefs, and escalating decisions.

Run one group or explicit task-ID chunk at a time. Worker assignments and planning headings are not review boundaries: use the reconciled review plan below to decide when independent acceptance is required. Workers have task-scoped repository access within the selected action context, not file-ownership whitelists: they edit whatever the assigned tasks require while preserving unrelated work and recorded intent. Read-only investigations may run concurrently when independent; implementation workers do not. Human-input branches pause execution and resume explicitly with the user's answer.

## Review plan and checks

Preparation returns an explicit review plan with:

- Identity: selected repository/worktree, change/store, schema, CLI state, progress, and context paths.
- Coverage: exact task IDs (mapping CLI IDs to human IDs when different), requirements/contracts, ordered groups and explicit task-ID chunks where necessary.
- Dependencies: dependency edges naming the prerequisite contract and dependent tasks, risk classifications with rationale, review boundary membership, and prerequisite release conditions.
- Checks: discovered focused and required final check commands, working directories, covered scope, and relevant environment assumptions.
- Continuity: invocation/preparation context policy, established host capabilities, finite checkpoints, safe record location, source bindings, and writer/subprocess state.

Discover checks from repository instructions and executable configuration once during preparation; pass the applicable commands in worker briefs rather than reconstructing them in every prompt. Workers return exact commands, results/exit status, covered scope, and inspected source binding. Missing or blocked required checks are not passes. Executable checks are mechanical guardrails, not semantic acceptance.

Default each group to its own review boundary. Combine compatible lower-risk groups only with affirmative rationale that none consumes an unverified prerequisite contract; file independence or presentation labels alone do not establish safety. High-risk contracts include security/authorization, durable custody/storage, mutation admission/idempotency, recovery/reconciliation, and other consequential cross-component invariants. Unknown risk requires a separate boundary, not an optimistic low-risk classification. High-risk or uncertain prerequisites require independent acceptance and serialized bookkeeping before dependent work starts. Reconcile changed dependencies or risk assumptions before affected work proceeds; freeze affected dependents and split a planned batch when a new consequential prerequisite appears.

## Bounded workers and continuity

At invocation/preparation, record a configurable context policy, not a package configuration API. Default to a fresh worker per group even when review is batched. Split unusually large groups into explicit task-ID chunks with finite checkpoints and remaining-work criteria; split an oversized single task into bounded checkpoints under that same ID, retaining partial status. Pass concise reconciled records and required context, not the entire transcript. If no safe finite assignment fits established host limits, ask and pause before dispatch.

Use context telemetry only when the invoking host establishes a reliable context-occupancy signal: record capability evidence, units, interpretation, observation cadence, and a configured safe-boundary handoff threshold. There is no universal token threshold. Cumulative billed input tokens are not context occupancy. Without reliable telemetry, use finite assignments and planned checkpoints; do not promise automatic threshold detection. Approaching a supported threshold triggers cooperative checkpoint/handoff, not forced interruption or completion of unfinished work.

Before writing any plan, handoff, finding or ledger, select a configurable repository-local per-change directory within the allowed action context (default `.openspec-orchestration/<change>/`). Resolve the physical path, check repository ignore status with `git check-ignore`, and confirm `git ls-files` finds no tracked records. Revalidate on resume. Unsafe storage requires an already ignored location or a pause before writes; preserve ignore policy and never force-add records. Read [record templates and source-binding rules](./references/records.md) during preparation and before creating or reconciling evidence. Keep all run evidence out of planning artifacts and commits; avoid credentials and personal data. Missing records require fresh reconstruction, not inferred acceptance.

At each safe checkpoint, persist a source-bound handoff and return, leaving unfinished or unverified tasks pending. Before **any** implementation, replacement, repair, correction or bookkeeping writer, require confirmed previous writer termination plus reconciliation that no surviving subprocess can mutate source. Use only capabilities established by the invoking host; record exit/process evidence and known subprocess state. A returned summary alone is not subprocess quiescence. An interrupted writer with uncertain termination or subprocess state blocks every successor writer: preserve progress, ask and pause; invent no stop API. Read-only work is concurrent only when it cannot mutate the inspected scope or disrupt evidence capture.

Reconcile actual source, tasks, prerequisite assumptions and process state on resume and before dispatch, acceptance or bookkeeping. Compare scoped content fingerprints (tracked/index, dirty/staged, untracked source and deletions) and recorded state, not just HEAD, timestamps, line numbers or the worker's edited-file list. Capture source before and after checks/review; reconcile intervening changes before reuse or acceptance. Changes to source, shared contracts, dependencies, check configuration or environment assumptions invalidate affected check/semantic evidence and downstream dependent evidence; uncertain impact invalidates the affected boundary. Rediscover/rerun affected commands. A whole-tree change alone does not invalidate demonstrably unchanged scope. Ignore local ledger churn and known checkbox-only bookkeeping, while task meaning or requirement edits invalidate relevant mappings.

Keep `implementation`, `checks`, `semantic acceptance` and `bookkeeping` statuses separate with reasons and affected dependents. Freeze affected dependent release immediately when acceptance becomes stale. Previously bookkept tasks with invalidated acceptance cannot authorize release or completion: after writer quiescence, serialize correction of only affected checkboxes/statuses, preserve unrelated completed tasks, and require fresh independent review/reacceptance and bookkeeping before release. Checked boxes and HEAD-only equality are not current acceptance.

## Repair verification

Persist each technical finding using the finding template in `records.md`: stable ID, violated requirement/task, file/line anchored to a source binding, reproduction/failing regression or explicit limitation, expected behavior, affected contracts/dependents, and regression scope. A missing reproduction requires independent source-bound investigation, not an invented test pass. Missing, incomplete or invalidated acceptance without an actionable technical finding requires fresh inspection of the affected boundary/dependents, not an empty repair treated as resolved. Repair briefs carry these findings, current source/plan, and reconciled accepted unaffected evidence.

Delegate a fresh independent read-only **repair reviewer**, separate from the repair worker. Start with the actual repair, finding reproduction/regression, and affected contracts; the reviewer controls verification scope and explicitly justifies why targeted coverage is sufficient. Bounded, regression-backed repairs with unchanged outside evidence need not repeat the whole group's review. Architecture changes, widened scope, changed shared assumptions, invalidated evidence, or uncertain impact expand review to the affected boundary and dependent contracts or wider scope. Reconcile/invalidate affected records and adjust release conditions before acceptance; a repair worker's narrow scope claim is not authority. Preserve demonstrably unaffected evidence with reasons. Capture before/after source bindings for repair checks and review.

Technical repairs within recorded intent proceed autonomously. Genuine design/product/architecture or authorization decisions pause for input; recurring findings with no edits and no new evidence pause instead of redispatching an unchanged brief. An expanded review is not permission to choose a new architecture.

## Stage contracts

1. **Prepare.** Spawn a read-only `general-purpose` Agent to read and follow `openspec-apply-change` through change selection, status, apply instructions, and context loading. Pass the repository path and requested change/store. Require the explicit review plan above, derived from current apply context and all required context files, plus the continuity policy and validated storage. Establish host capabilities rather than assuming telemetry or termination APIs. Likely touched files are advisory, not edit restrictions. Preserve blocked/all-done states and ask the user if selection is ambiguous.
2. **Schedule.** Order groups/chunks by dependency and reconcile the plan against actual state before dispatch. Run sequential workers within a justified lower-risk boundary without inserting review after every heading or worker return. Release work only when its prerequisite release conditions hold; required prerequisite acceptance and bookkeeping cannot be deferred to the end of a batch. Retain accepted evidence for subsequent workers and reconcile it against actual state on resume. Do not build file-ownership plans.
3. **Implement and repair.** Give a `general-purpose` Agent the repository path, exact change/store, assigned task ids, prerequisite evidence, implementation skill path, and any prior findings with reproduction evidence. Require it to read the implementation skill and project instructions, implement only its assigned group/chunk, run the plan's focused repository-provided checks, persist a source-bound checkpoint/handoff and finish at the configured finite boundary, and return implemented task IDs and requirement coverage, actual changed files, exact commands/results with scope and source binding, and blockers. Override the skill's whole-change loop and pause-on-technical-error rule: stop after the assignment, and repair technical failures autonomously within recorded intent. Editing another file the tasks require is not added scope. Keep task-checkbox updates pending for bookkeeping. Genuine design, product, architecture or authorization decisions still require input; preserve user interruptions and action-context constraints.
4. **Verify boundary.** At each planned or newly required boundary, spawn a fresh independent read-only Agent, separate from its implementation workers. Require actual-source inspection against all boundary task IDs and requirements, cross-component contracts, relevant failure/cancellation/restart/concurrency behavior, prerequisite regressions, and whether checks reach production paths. It may require additional checks or reproductions; avoid repeating broad suites without a coverage reason. A worker summary or passing checks cannot substitute for semantic review. A semantic defect keeps the boundary unaccepted even with green checks. Route technical findings through the repair verification rules above, then require fresh reviewer-controlled acceptance of the repair and affected contracts. If the same findings recur with no edits and no new evidence, report the impediment and ask rather than redispatching unchanged work. Keep task-checkbox updates pending until the applicable review boundary passes. After source reconciliation and acceptance, and only with confirmed writer/subprocess quiescence, a separate serialized bookkeeping writer marks only fully implemented, independently verified task IDs complete and confirms fresh apply progress before releasing work that requires that prerequisite. Unaccepted tasks stay pending.
5. **Finish.** After every applicable boundary is independently accepted and bookkept, reconcile source/prerequisites and delegate fresh required repository-wide checks from the plan, a fresh independent read-only integrated semantic review against the whole change/current source and cross-component requirements, and a current apply-status read. This same Finish path is mandatory on resumed all-done: skip ordinary implementation dispatch, not final verification. Intermediate acceptance or earlier green checks cannot substitute for fresh integrated evidence. Bind checks/review to before/after source and assumptions; reconcile changes before acceptance. Final commands that can mutate source obey the same writer/subprocess quiescence rules before review or another writer. Final technical defects enter the targeted repair loop above; invalidate affected final evidence, rerun affected required final checks and refresh affected integrated review with fresh independent scope justification (expand when uncertain), then reread current apply status. A pre-repair integrated result cannot authorize a changed contract. Claim completion only when all specified tasks are implemented, independently accepted and bookkept, current apply status confirms completion, all required final checks pass, integrated review is fresh, and no blocking findings, blocked required checks or stale prerequisite acceptance remain. Pause for genuine decisions or missing authorization.

## Reporting and authorization

On completion, pause, or handoff, fill a **current-task-status report**. The report is complete only when every relevant exact task ID (with CLI/human mapping where needed) has current implementation, checks, independent semantic acceptance, and bookkeeping states. Give reasons and evidence/provenance references, distinguishing observed source/checks, supplied historical claims, and independently produced acceptance. Use explicit `none` for empty ID sets and `unknown` with a limitation for unestablished states or provenance; never invent historical acceptance. Distinguish observed checkbox state from verified bookkeeping. Separate remaining implementation task IDs from pending independent acceptance, bookkeeping, and final-assurance work. Checked counts or proposed future record fields are not substitutes for filled current states.

Also report selected repository/worktree/change/store and schema; actual changed files; boundary coverage and risk/release rationale; commands/results/covered scope and skips or blocked required checks; source bindings, evidence freshness, retained/invalidated evidence and required refresh; unresolved findings/blockers and host limitations (including telemetry/quiescence). Keep proposed steps separate from observed actions, and structural checks separate from semantic/runtime evidence. Report partial progress without implying completion.

Implementation acceptance grants no delivery authorization. Committing, pushing, spec syncing and archiving remain separate authorized requests under existing policies. Preserve any explicit prior authorization and its conditions, but execute those actions only in their separately authorized procedure after required verification; never infer permission from green checks, accepted evidence, all-done status, or a fixture. This skill does not perform them.
